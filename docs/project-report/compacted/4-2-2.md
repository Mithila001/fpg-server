### Chapter 4.2.2 Build Requirement

The build requirement stage is the formal pre-processing layer of the floor plan generation pipeline. It does not synthesize geometry directly; instead, it converts a loosely specified user request into a validated, solver-ready requirement package. This stage acts as a semantic and numerical normalization boundary by ensuring that the optimization process receives coherent room definitions, floor dimensions, and relational constraints. By doing so before the solver is invoked, the system reduces infeasible trials, limits unnecessary search space, and enforces a consistent interpretation of the design brief.

At a high level, the stage performs three tasks: it validates the room template, retrieves constraint knowledge stored on the server, and mutates the request so all values are compatible with generation. The result is a consolidated requirements object used in later optimization, scoring, and post-processing phases.

#### Validation

Validation first checks whether the room template contains the mandatory room categories required for meaningful floor plan generation. A small illustrative example includes a sleeping room, a kitchen, a bathroom, and a veranda or similar access-related space. These are mandatory because the downstream solver expects a minimum semantic structure from which it can derive adjacency, circulation, and envelope relationships. Without these foundational room types, the constraint system would have insufficient information to construct a viable household composition.

This step also prevents the solver from operating on ambiguous or incomplete room templates. Since optimization is driven by constraints, missing structural elements can lead to infeasible relationships later in the pipeline. The validation layer therefore safeguards against both logical inconsistency and computational waste by establishing the minimum semantic completeness required for generation.

#### Dimension Calculation and Aspect Ratio

A second function of the build requirement stage is to estimate a suitable floor envelope from the room composition. This matters because the search space of a floor plan generator grows rapidly with available area. If the boundary is too large, the solver must explore many more placements, reducing efficiency and increasing the likelihood of weak solutions. To avoid this, the system reduces the effective floor space according to the minimum spatial requirements implied by the room set.

Let the minimum width and height of room $i$ be $w_i^{\min}$ and $h_i^{\min}$, and let the corresponding maximum values be $w_i^{\max}$ and $h_i^{\max}$. A conservative lower bound on the total area required by the template is

$$
A_{\min} = \sum_{i=1}^{n} w_i^{\min} h_i^{\min} + A_{\text{buffer}}.
$$

Likewise, an upper bound is

$$
A_{\max} = \sum_{i=1}^{n} w_i^{\max} h_i^{\max} + A_{\text{buffer}}.
$$

The buffer term $A_{\text{buffer}}$ provides extra allowance for circulation loss, alignment overhead, or auxiliary spacing.

The aspect ratio is handled through a feasibility test against the buildable envelope. If the requested ratio is

$$
r = \frac{H}{W},
$$

then the system seeks a rectangle that respects both the ratio and the available limits. Given maximum floor width $W_{\max}$ and maximum floor height $H_{\max}$, the largest feasible width is constrained by

$$
W \le W_{\max}, \qquad W \le \frac{H_{\max}}{r}, \qquad W \le \sqrt{\frac{A_{\max}}{r}}.
$$

The selected width is therefore

$$
W^* = \min\left(W_{\max},\, \frac{H_{\max}}{r},\, \sqrt{\frac{A_{\max}}{r}}\right),
$$

and the corresponding height is

$$
H^* = rW^*.
$$

If the resulting rectangle still fails to meet the minimum required area, the request is rejected as geometrically incompatible.

#### Load Server Constraints

Once the request has been validated geometrically, the system loads server-side constraints defining the allowable behavior of each room type. Room-size constraints specify admissible width, height, and area ranges for a room category under a particular size label. Relation constraints describe how one room type should interact with others, including the subject room type, related room types, and an enforcement level indicating whether the relation is mandatory or preferential. These loaded constraints become part of the solver’s formal objective and feasibility structure.

#### Majority Size Selection and Prune Relations

The build requirement stage also normalizes room size labels. If several size labels appear in a template, the system selects the most frequent one and promotes it as the dominant category, converting all rooms to that category except where a special case is preserved. This reduces heterogeneity and stabilizes the constraint set.

Afterward, relation constraints are pruned so that only relationships relevant to the actual template remain. This prevents the solver from enforcing rules involving room types that are absent from the request. The pruning step aligns the knowledge base with the active template and avoids meaningless or impossible conditions.

#### Assemble Final Package

After validation, geometric adjustment, constraint loading, size normalization, and relation pruning, the stage assembles the final requirements package. It contains the normalized room list, validated configuration values, and filtered relation constraints. This package becomes the canonical input for later phases of the floor plan pipeline.

Overall, the build requirement stage is the methodological foundation of the floor plan generation system. It transforms an informal design brief into a structured optimization input, ensuring that the solver operates within a meaningful and feasible search domain. By mediating between human intent and machine-enforced constraints, it improves stability, reduces infeasible trials, and supports a more reliable interpretation of spatial requirements.
