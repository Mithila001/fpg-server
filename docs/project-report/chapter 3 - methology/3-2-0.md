Requirement Gathering

## Technology Stack

The project is built on a Python-centred backend stack designed to support constraint-based architectural generation, spatial validation, and asynchronous job processing. A modern web API framework provides the external interface for receiving land data, room requirements, and generation requests, while an ASGI server supports efficient request handling and streaming responses. Data modelling and validation are managed through typed schema objects, which improves consistency across the request, service, and persistence layers. For storage, the system relies on a relational database, giving it a structured foundation for regulation profiles, room templates, constraint records, and job-related state. The database layer is integrated through an object-relational approach, which reduces duplication between schema definitions and query logic.

At the computational level, the stack combines several specialist libraries to address different aspects of the planning problem. A constraint programming engine is used to search for feasible room arrangements under strict geometric and regulatory conditions. Numerical and scientific packages support spatial calculations, optimization support, and geometric processing, while computational-geometry utilities assist with boundary handling, intersection logic, and plan refinement. Additional libraries are used for score evaluation, optimization experiments, and visual output generation, which together allow the project to move from raw requirements to a rendered and assessable floor plan. Development quality is reinforced through automated testing and linting tools, ensuring that the software remains reliable as the constraint set and architectural rules evolve.

## System Architecture

The system follows a layered and service-oriented architecture in which user requests are separated from the computational core. The external interface submits site geometry, dimensional limits, and room requirements to the application layer, where the input is first validated and normalized. A job-management layer then creates an asynchronous task, enabling long-running generation operations to proceed without blocking the interface. Progress updates are delivered through streamed events, allowing the user to observe the state of the search process in near real time. This design is particularly appropriate for floor-plan synthesis, because the solver may require multiple phases of exploration, refinement, and post-processing before a satisfactory result is produced.

Behind the service layer, the application is organized into distinct functional modules. One module derives the buildable area from site constraints and setback rules; another transforms the validated requirements into a solver-ready configuration; a third performs the actual spatial search using constraint programming; and subsequent modules refine the geometry, generate openings, score the result, and prepare the output for presentation. The persistence layer stores configuration data, templates, and constraint definitions so that the generation process can be adapted to different regulatory profiles without redesigning the entire system. This separation of responsibilities improves maintainability, supports extensibility, and makes the overall architecture suitable for academic and practical deployment alike.
