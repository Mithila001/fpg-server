# Existing Generated Floor Plan Scoring Setup — Characteristics

**Status:** Existing legacy implementation used as a source of behavioral knowledge.

The existing generated floor plan scoring setup is located under:

```text
app/algorithms/fgp_score/
```

It is separate from the older scoring implementation inside `app/algorithms/fpg_rooms/fpg_score/`.

## Main Characteristics Existing Setup

### 1. Central Score Manager

The scoring process is controlled by a single `score_manager()` function.

It is responsible for:

* preparing the floor plan for scoring,
* removing unsupported or irrelevant rooms,
* validating the floor-plan geometry,
* manually calling each scoring function,
* combining the individual results,
* building the final score report,
* and printing diagnostic information.

This makes the score manager both an orchestrator and a place containing scoring policy.

### 2. Critical and Functional Scoring Categories

The setup separates scoring into two broad sections:

```text
score_critical/
score_functional/
```

Critical checks currently include:

* room adjacency validation,
* empty-space validation,
* inward-pocket detection.

Functional scoring includes:

* basic room-function checks,
* experimental path-simulation scoring.

### 3. Critical Checks Act as a Gate

Critical checks are evaluated first.

The current implementation calculates a critical score out of `25`. Functional scoring is only executed when the full critical score is achieved.

Therefore, the current behavior is approximately:

```text
Critical checks fail
    → return only the partial critical score

All critical checks pass
    → calculate functional score
    → combine critical and functional scores
```

### 4. Scoring Contributions Are Hardcoded

The score manager directly controls:

* which evaluators run,
* their execution order,
* score ranges,
* gating behavior,
* and how results are combined.

Adding, removing, disabling, or reweighting an evaluator requires editing the manager code.

There is no evaluator registry, scoring profile, or configuration-driven evaluator selection.

### 5. Evaluators Do Not Share a Standard Interface

Different scoring functions return different structures.

Examples include:

* lists of violation messages,
* boolean violation results,
* tuples containing violations and diagnostics,
* numeric scores,
* specialized result dataclasses.

The score manager must understand each evaluator’s specific function signature and return format.

### 6. Inputs Depend on Existing Project Types

The main scoring entry point receives:

```text
FloorPlanWithOpenings
FpgRequirements
```

Individual evaluators may also depend directly on:

* processed room objects,
* relation-constraint objects,
* configuration values,
* Shapely geometries,
* string-based room types.

The scoring package does not currently define a dedicated normalized scoring input contract.

### 7. Configuration Is Distributed

Scoring-related configuration exists in multiple places, including:

* the generation requirements configuration,
* shared project configuration modules,
* constants inside scoring modules,
* path-simulation-specific configuration.

There is no single configuration model representing the complete generated-floor-plan scoring policy.

### 8. Diagnostics Are Important but Inconsistent

The setup returns useful information such as:

* passed and failed checks,
* violation messages,
* adjacency diagnostics,
* empty-space diagnostics,
* inward-pocket diagnostics.

However, diagnostic structures differ between evaluators and often use loosely structured dictionaries.

### 9. Geometry Validation Happens Before Scoring

The manager first verifies that the post-processed floor plan is rectilinear.

When this verification fails, the scoring process stops and returns an empty or zero-valued result rather than running the normal evaluators.

### 10. Room Filtering Happens Inside the Manager

Before scoring, the manager creates a filtered copy of the floor plan.

It currently excludes:

* outdoor veranda rooms,
* rooms with insufficient vertices.

This preparation behavior is embedded directly inside the score manager.

### 11. Development and Production Concerns Are Mixed

The package contains development utilities such as:

* plotting,
* console printing,
* temporary path-simulation visualization,
* commented debugging calls,
* placeholder scoring behavior.

Some experimental functionality exists beside the active scoring code.

### 12. Path Simulation Is a Large Internal Subsystem

The functional path-simulation section contains its own:

* graph construction,
* path finding,
* simulation models,
* scoring functions,
* configuration,
* diagnostics,
* plotting utilities.

It behaves almost like an independent feature but currently sits inside the general scoring package.

### 13. Naming and Result Semantics Are Not Fully Consistent

Some names suggest that fields contain only critical scores, while the manager may place the combined final score into those fields.

Score ranges also vary between sections, for example:

* critical score out of `25`,
* functional contribution out of `75`,
* internal path metrics based on `0–100`.

### 14. The Setup Is Procedural and Explicit

The current architecture is straightforward and easy to trace for a small number of evaluators:

```text
Prepare floor plan
    ↓
Validate geometry
    ↓
Run critical check A
    ↓
Run critical check B
    ↓
Run critical check C
    ↓
Calculate critical score
    ↓
Optionally run functional scoring
    ↓
Build result
```

Its main limitation is that the manager must be changed whenever the scoring system grows or its policy changes.

## Overall Summary

The existing setup contains useful scoring behaviors and geometry-analysis logic, but its framework is mainly a manually coordinated collection of scoring functions.

Its defining characteristics are:

* one central procedural manager,
* critical and functional categories,
* critical-score gating,
* hardcoded evaluator execution,
* inconsistent evaluator contracts,
* distributed configuration,
* useful but loosely structured diagnostics,
* and development logic mixed with active scoring behavior.

The internal evaluator logic can be reused as behavioral reference, but the surrounding management structure does not need to be preserved in the replacement.
